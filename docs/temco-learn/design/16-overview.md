# 16 — The platform in one document

What Temco Learn produces, who does what, and what does not change.

---

## What a reader gets, and what an author gets

**A published documentation site** covering every product: one searchable site, one page per topic, a snapshot per release, and an editor — a page is opened, corrected and published from the center tool or from VS Code, with the same "edit this page" path leading back to the source in git. The site is not the engine's output: it reads content packages and puts its own navigation, search, downloads and assistant over them.

The site is not bespoke software. It is generated by the same class of engine Microsoft built its own documentation on, which is why the only code this project owns is its content, its structure and its rules.

The single source that feeds the site also produces the offline help file that ships with each installer, so nothing about the reader's experience depends on a website being reachable.

Three boundaries are deliberate:

- **the center tool is internal.** It is not part of a customer installation, and it does not require a product to be running;
- **an engine is a tool behind a contract.** DocFX is the default; a product may use another one, and the site never learns which;
- **only artefacts ship.** A customer installation receives the help file and the F1 map inside the application. No editor, no AI, no authoring tooling — ever.

## How one commit becomes updated documentation

Time runs down the diagram. Only two people act: the developer who commits, and the owner who approves.

```
  developer            git              PLATFORM (AI)            maintainer      outputs
      │                 │                    │                       │             │
      │ commit          │                    │                       │             │
      ├─────────────────►                    │                       │             │
      │                 │ trigger            │                       │             │
      │                 ├────────────────────►                       │             │
      │                 │                    │ 1 summarise change    │             │
      │                 │                    │ 2 find affected pages │             │
      │                 │                    │ 3 draft page edits    │             │
      │                 │                    │ 4 list pages owed     │             │
      │                 │                    │                       │             │
      │                 │                    │ ready to review       │             │
      │                 │                    ├───────────────────────►             │
      │                 │                    │ approved              │             │
      │                 │                    ◄───────────────────────┤             │
      │                 │ documentation commit                       │             │
      │                 ◄────────────────────┤                       │             │
      │                 │                    │                       │             │
      │                 │ publish            │                       │             │
      │                 ├────────────────────┼───────────────────────┼─────────────►
      │                 │                    │                       │ help file · │
      │                 │                    │                       │ the site ·  │
      │                 │                    │                       │ the PDF     │
      │ nothing to do   │                    │                       │             │
```

| Step | Who | Effort for the developer |
|---|---|---|
| write the commit | the developer | none — they already do this |
| summarise the change, find the pages, draft the edits, list the gaps | the platform | none; it is automatic |
| approve or correct the prose | the page owner, by default the docs owner | minutes |
| publish the help file, the site and the PDF | the platform | none; it is automatic |

**The AI proposes; a person disposes.** Nothing reaches a customer without a named person approving it, every change is a git commit that one command reverts, and no AI process holds publish rights.

## Many products, one documentation system

```
  build time — one source, many outputs

   products/*/docs ──┐
                     ├──►  THE PLATFORM  ──►  the site      all products, one search
   shared/glossary ──┘                    ├──►  help file   only that product's pages
                                          ├──►  PDF         one per release
                                          └──►  F1 map      page id → help topic, per application
```

1. **content never moves.** A product's pages stay in that product's repository, next to the code they describe. Adding a product to the site is a mapping entry, not a content migration.
2. **one search over everything.** The site indexes every product together; each installer carries only its own product's pages.
3. **federated ownership.** Each product's pages have their own owner, and the platform owner owns the cross-product pages.
4. **cross-product links are declared**, so the site can resolve them and the offline help file can degrade them to plain text.
5. **per-release snapshots**, so a customer on an older build can read the documentation for that build.

## Many devices without duplicated pages

```
   one page, many device models — the text is written once

   registry entry:  "PID Control" ──► variants:  T3-TB    T3-NB    T3-LB    T3-BB
                                                     │        │        │        │
                                                     └────────┴───┬────┴────────┘
                                                                  ▼
                             rendered once per variant; shared sentences are reused
                             edit the shared text once and every variant follows
                             variant-only text lives in a clearly marked block
```

A device model is a **variant of a page**, not a new page. That is what prevents today's situation from being recreated at three times the size as more products arrive.

## Who does what

| Role | Responsibility |
|---|---|
| developer | commit code, and write one clear commit line |
| docs owner — the platform owner | review the drafts, own the registry, run publishing, read the staleness report |
| page owner, per product or area | approve prose changes in that area and keep claimed pages true |
| reviewer and release owner | approve the documentation snapshot for a release |
| management | name the owner, approve the platform as internal tooling, approve the model policy |

## Capabilities

| Capability | The help tooling today | This platform |
|---|---|---|
| annotated screenshots and callouts | yes, maintained by hand | yes, the same mechanism, plus an image audit that reports missing, unused and duplicate images |
| context-sensitive F1 help | yes, a topic map | yes, the same kind of map, generated from the registry so it cannot drift |
| an offline help file | yes, the shipping artefact | yes — unchanged pipeline and unchanged artefact |
| a documentation site | no | yes: one searchable site for every product |
| a PDF per release | ad hoc | yes, generated from the same source |
| version snapshots | no | yes: the documentation for each release tag |
| commit summaries | no | **yes — already running** |
| AI-drafted page updates | no | yes, draft only, with human approval |
| "ask the documentation" offline | no | yes — a local model, no internet and no keys |
| cross-product search | no | yes |
| a staleness and health report per area | no | yes |

## The AI, and why it runs locally

- The model runs **on the authoring machine**. No cloud service, no API keys, no monthly bill, no documentation text leaving the building, and it works in a room with no internet.
- Model weights are downloaded once and stored on disk, and models under permissive licences (Apache or MIT) are preferred so distribution is never restricted.
- The guardrails are: draft only, no publish rights, every suggestion an ordinary git change, prompts versioned in the repository, and the model itself a setting rather than something baked into the platform.
- Because the model is a setting, a different or larger one can be adopted later without redesigning anything.

## Risks and how each is contained

| Risk | Containment |
|---|---|
| the AI writes something incorrect | draft only; a named person approves; every change is a git commit; one-command rollback |
| documentation drifts again in a year | the commit pass lists the pages still owed, CI reports it, and the health report shows it per area |
| a key person leaves | content, the registry and the rules live in git; approving is the only manual step, and any engineer can do it |
| model licensing limits distribution | permissive models only, recorded with their licence |
| confidential material leaving the building | a local model, no egress and no keys; the platform is internal |
| the platform becomes a maintenance burden | an extension rather than a fork wherever possible, and a publishing engine that is pinned rather than patched |

## What does not change

- the developer's workflow: nobody is asked to write, format or review documentation unless they want to;
- the customer-facing artefact: the help file ships exactly as it does today, and F1 help is unchanged;
- where the pages live in the repositories;
- what a customer installation contains: the help file, and nothing else from this platform;
- the engine decision: pinned, patchable and replaceable ([02](02-docfx-engine.md)).

## Decisions that need management

1. **Name the documentation owner** — one person accountable for the platform and for approvals.
2. **Approve the platform as internal tooling** — it runs on the team's machines, and only its outputs ship.
3. **Approve VS Code as the shell** for the authoring side, with a branded installer left as an optional packaging step.
4. **Approve the local-AI approach** — offline models, no cloud, permissive licences only.
5. **Approve per-product publishing** — each installer carries only its own product's help pages.
